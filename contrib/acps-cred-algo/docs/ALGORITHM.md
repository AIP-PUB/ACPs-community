# 算法说明

本文档解释 `acps-cred-algo` 的公式来源、参数取值依据、设计取舍与已知局限。

---

## 一、符号

| 符号 | 含义 |
|---|---|
| `n` | 参与统计的凭证数（不含中性终态） |
| `s` | 其中成功数 |
| `f` | 其中失败数（`s + f = n`） |
| `w_i` | 第 `i` 条凭证的衰减权重 |
| `W` | 衰减后总权重，`W = Σ w_i` |
| `k` | 置信度先验强度（`prior_weight`） |
| `z` | 正态分位数（95% → 1.96） |

---

## 二、Wilson 置信下界

对二项分布的成功率 `p`，其 95% 置信区间下界为：

```
         p̂ + z²/(2n) - z·√( p̂(1-p̂)/n + z²/(4n²) )
  LB  =  ──────────────────────────────────────────
                    1 + z²/n

其中 p̂ = s / n
```

实现见 `reputation.py: wilson_lower_bound()`。

### 为什么用下界而不是点估计？

| 情形 | p̂ | LB |
|---|---|---|
| 1/1 | 1.000 | 0.207 |
| 3/3 | 1.000 | 0.438 |
| 9/10 | 0.900 | 0.596 |
| 98/100 | 0.980 | 0.930 |

点估计会让「只被试过一次且成功」的智能体拿到满分，这在小样本场景下是危险的：
它可能只是运气好，也可能只是没遇到困难任务。下界把「证据不足」直接体现为分数低，
**不需要额外的人工阈值**。

## 三、多因子合成

```
base       = λ · LB + (1 - λ) · latencyScore
latencyScore = min(1, budget_ms / latencyEwma)
confidence = W / (W + k)
diversity  = min(1, 0.6 + 0.2 · max(1, distinctProviders))
freshness  = 1.0 （正常） 或 stale_acs_factor （证据早于 ACS 修改）

cred01 = confidence · diversity · freshness · base
cred   = round(100 · clamp(cred01, 0, 1), 2)
```

### 3.1 为什么 `confidence` 用权重而非条数？

设 `W = Σ w_i`，`w_i = 0.5^(age_i / half_life)`。

若用条数 `n`：批量补录 100 条三年前的凭证，会让 `n/(n+k)` 迅速接近 1，
从而拿到高置信度 —— 这是典型的刷分路径。

用 `W`：三年前的凭证 `w ≈ 0.5^(1095/14) ≈ 10^-24`，几乎不贡献置信度。
**攻击者无法通过「补历史」提升分数，只能通过「持续产生新证据」。**

### 3.2 为什么 `latencyScore` 用倒数值而非线性映射？

`budget_ms / latency` 在时延接近 0 时会爆炸，所以取 `min(1, ...)` 截断。
这样：

- 时延 ≤ `budget` → 满分 1.0（不再奖励「更快」，避免无意义的军备竞赛）
- 时延 > `budget` → 按比例衰减（超时越多分越低）

在预算以上，倒数映射使得时延越大时，每增加同样的时长，分数下降越小；
在预算以内，分数保持 1.0。因此从 200ms 降到 100ms 不会额外加分。

### 3.3 为什么是乘法而不是加权求和？

因为每个因子都是**否决式的必要条件**：

- 证据不足（`confidence` 低）→ 不该给高分
- 来源单一（`diversity` 低）→ 可能是刷的
- 证据过期（`freshness` 0.5）→ 能力可能已经变了

加权求和会让某一项的高分补偿另一项的低分，这在「可信度」语义下是错误的：
**一条来自单一来源的过期证据，不可能因为「成功率 100%」就变得可信。**

### 3.4 多样性因子的取值

`min(1, 0.6 + 0.2 × 来源数)`：

| 来源数 | 因子 |
|---|---|
| 0（无来源信息） | 0.8 |
| 1 | 0.8 |
| 2 | 1.0 |
| ≥3 | 1.0 |

来源数为 0 时给 0.8 而不是 0，是为了兼容不支持 `issuerProvider` 字段的实现 ——
否则它们的所有凭证都会被判为不可信。

## 四、CredRank 排序

```
semantic_i = 0.1 + 0.9 · (1 - (r_i - 1) / (R - 1))      ← r_i: 语义排名, R: 最大排名

combined_i = α · semantic_i + β · (cred_i / 100)
```

排序：`combined` 降序；同分时按 `r_i` 升序（语义原本更靠前的优先）。

### 4.1 为什么 `semantic` 有 0.1 下限？

保留 0.1 的下限，使末位候选也具有非零的语义分量。
这不是相关性过滤器，也不保证相关性较低的候选不能反超；
调用方仍需在发现阶段筛选符合任务要求的候选。

### 4.2 α / β 的取值

默认 `α=0.4, β=0.6`。取 `β > α` 的理由：

- 语义分是「声明层」的信号，可信度是「行为层」的信号，后者更难伪造；
- 但 `α` 不能太低，否则等于绕开发现服务自行选型，失去与标准的兼容性。

### 4.3 探索配额的必要性

纯 `combined` 排序的稳态：冷启动智能体 `cred = 20`（名义分），
在语义分相同的情况下永远排在已有证据的智能体之后。

这形成一个正反馈死锁：

```
没证据 → 排最后 → 没调用 → 没证据
```

`explore_quota` 在序列前 `explore_slot` 位保留名额给冷启动候选，
代价是可能牺牲少量排序精度，收益是**打破死锁、让新智能体获得初始证据**。

这是信誉系统在工程上最容易被忽视、也最容易被追问的一点：
**一个只看历史数据排序的系统，会系统性地压制新进入者。**

## 五、参数敏感性

以下为在典型数据（10–20 条凭证、成功率 0.6–0.95）下的观察：

| 参数 | 变化 | 影响 |
|---|---|---|
| `half_life_days` | 7 → 30 | 分数对近期表现更敏感 → 更平滑；过短会导致剧烈波动 |
| `prior_weight` k | 3 → 10 | k 越大，样本要求越高，冷启动期越长 |
| `wilson_z` | 1.64 → 2.58 | z 越大越保守（90% → 99% 置信） |
| `min_samples` | 3 → 5 | 更多样本才脱离冷启动，防止 3 条好评就判高分 |
| `success_weight` λ | 0.5 → 0.9 | λ 越大越重视成功率，越轻视时延 |
| `explore_quota` | 0 → 2 | 探索名额越多，新智能体曝光机会越大，排序精度略降 |

**建议**：优先调 `min_samples` 与 `prior_weight`，它们对「防刷」最直接；
`success_weight` 按业务对时延的敏感度调整。

## 六、设计取舍

### 6.1 为什么在客户端排序，不改发现服务？

改发现服务等于自造一套发现语义：

- 破坏与既有实现的兼容；
- 跨域转发链（forwardChain）中下游无法识别；
- 无法回退。

本库只**消费**标准发现结果，在调用方侧做本地二次排序 —— 纯客户端行为，零兼容成本。

### 6.2 为什么凭证不新增协议字段？

凭证只描述「谁、何时、用了什么技能、结果如何、耗时多少」，全部可由标准结果对象推导。
因此它可以作为**可被完全忽略的附加数据项**传递：不支持的实现直接跳过，不报错。

### 6.3 为什么不直接用机器学习模型？

- **可解释性**：每个中间量都能算给人看，评委/审计方能复核；
- **数据量**：冷启动场景下没有足够样本训练模型；
- **抗对抗**：线性模型和树模型都可能被针对性构造的样本欺骗，
  而 Wilson 下界有明确的统计语义。

如果未来积累了大量数据，可以在本库的输出之上再叠一层学习排序（LTR），
而不是替换它 —— 本库提供的是**特征与基线**。

## 七、已知局限

1. **`issuerProvider` 依赖调用方如实填写**。若整条链路都由同一方伪造，本库无法识别
   —— 这是「第三方回查」需要解决的另一半问题（见主工程的 `verify.py`）。
2. **中性终态（`canceled`）被排除在分母外**。若某方大量制造「取消」来规避失败记录，
   会导致成功率虚高。工程上应结合取消率单独监控。
3. **时延受网络环境影响**。跨地域调用会被系统性低估，建议按区域分组统计后合并，
   或使用调用方侧的服务端计时。
4. **`semantic_score` 假设排名连续且无并列**。若发现服务返回并列名次，
   需先做名次归一化。
5. **未指定 `acs_version` 时按凭证数量最多的版本组评分**，不保证是时间上最新的版本。调用方应显式传入当前版本。
6. **凭证摘要只对整条内容去重**。更换 `receiptId` 或其他字段会产生新摘要，不等同于任务级去重或签名认证。
7. **输入校验由调用方负责**。无法解析或晚于当前时间的时间戳按 0 天处理；未知终态会增加证据权重，但不增加成功/失败计数。应在入库前验证时间、状态和来源。
8. **未处理多技能联合评价**。当前按 `(AIC, skillId)` 独立评分，
   不反映「一个智能体整体是否可靠」。若需要整体画像，应自行做技能间加权。
