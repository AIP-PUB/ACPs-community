AMP: Agent Monitoring Protocol (ACPs-spec-AMP-v02.02)

# 1. Document Definition

This document is the standard definition of the Agent Monitoring Protocol (AMP) within the ACPs agent collaboration protocol system, version v02.02.

The full title of the document is ACPs-spec-AMP-v02.02.

Document authors: Ke Yu (Beijing University of Posts and Telecommunications), Xiaolian Guo (Beijing University of Posts and Telecommunications), Jun Liu (Beijing University of Posts and Telecommunications), Xiaofeng Hu (Beijing University of Posts and Telecommunications), Di Ma (Beijing University of Posts and Telecommunications).

# 2. Introduction to the Agent Monitoring Protocol

For agent interconnection to become a secure and reliable agent system, a complete Agent Monitoring Protocol is required to precisely control the operating state of agents and to accomplish standardized storage and full-link management of logs, so as to ensure that the state information of agents can be aggregated in real time and distributed in an orderly manner under a unified specification, providing agent registration servers, discovery servers and other agents with consistent state query and tracking capabilities, thereby providing core support for efficient collaboration among agents and for the secure and stable operation of the system.

# 3. Core Content of the Agent Monitoring Protocol

## 3.1 Logs

**Log files**
The carrier of the raw log data generated by an agent. Log files output by all agents should follow a unified outer encapsulation format to ensure that they can be generically forwarded and parsed; at the same time, different log content may be included according to business type under the unified framework, so as to meet the recording and tracking needs of different scenarios.

## 3.2 Agent Monitoring Architecture Framework

The agent monitoring framework can be divided into two layers:

- **Log collection layer**: Various types of logs (heartbeat, access, metrics, audit, message, system, etc.) are written by agents into local log files by type, and after the necessary steps such as parsing, filtering and tagging, this layer delivers the logs by type to the log storage layer in a reliable and controllable manner.

- **Log storage layer**: This layer is responsible for the unified storage of different log information from different agents. According to the structural characteristics, access patterns and lifecycle requirements of different log types, it provides differentiated storage solutions, and at the same time supports index construction and fast retrieval of log data, providing data support for subsequent monitoring analysis, alarm triggering and problem tracing.

# 4 Log Types and Their Main Functions

## 4.1 Log Types and Log Files

- **Heartbeat Logs**: Periodically record the operating state and health condition of an agent. The core purpose of heartbeat logs is to express the fact that "the agent is still alive". They are usually generated at a fixed period (e.g., every 10 to 60 seconds) and usually contain only lightweight information such as a status identifier and a brief metrics summary. Heartbeat logs are extremely time-sensitive and their historical data has low value, so a more aggressive downsampling and short-term retention strategy may be adopted for storage and transmission.

- **Metrics Logs**: Record the performance metrics and resource usage of an agent, focusing on recording "how the agent is performing", presented in the form of structured numerical values. Typical content includes task queue status, latency percentiles (P50/P90/P99), CPU/memory/disk/network utilization, etc.

- **Access Logs**: Record every interaction between an agent and external systems, including requests, responses, errors, debugging information and trace data. Access logs are "interaction logs in a broad sense", covering request logs, error logs, debug logs and distributed tracing logs in the traditional sense. The `severityText` field (`DEBUG` / `INFO` / `WARN` / `ERROR`) distinguishes severity levels, `traceId` / `spanId` support link tracing, and `correlationId` is used for business tracing. Access logs usually have a large data volume and diverse query patterns, and are suitable for storage in systems that support full-text search and aggregation analysis.

- **Message Logs**: Record the sending and receiving behavior of an agent through message channels (queues, topics, streams), focusing on reliable delivery, ordering and retry status in message-driven architectures. Unlike the synchronous request-response of access logs, message logs usually describe asynchronous, decoupled producer/consumer interactions. Typical fields include topic/queue, partition/offset, deliveryAttempt, eventType (boundary events such as send/receive/acknowledge/dead letter), etc. They help locate problems such as message backlog, out-of-order delivery and duplicate delivery, and can link event-driven chains across systems through `traceId` / `spanId`, as well as perform business tracing through `correlationId`.

- **Audit Logs**: Record security-related operations and access records of an agent. Audit logs serve the needs of security compliance and post-event forensics, and usually contain fields such as the operator, the operation object, the operation type and the operation result. Audit logs usually have a long retention period (depending on regulatory requirements) and have high requirements for integrity and immutability. Transaction logs of a billing system can also be classified as a special form of audit log.

- **System Logs**: Record status information of the agent's runtime environment and associated services, such as start/stop logs of associated services, database Slow Query logs, JVM GC logs, etc. System logs help diagnose problems in the agent runtime environment and are usually used in combination with access logs and metrics logs to obtain a comprehensive troubleshooting perspective. The body content of system logs adopts a **free format** and no unified structure is defined; each agent decides it on its own according to the characteristics of its own environment.

**Log files of different types**

To ensure the comprehensive performance, scalability and maintainability of the agent system, this specification recommends writing **by log type into separate files**, rather than writing all logs into the same file. For example:

- `heartbeat.log`: stores heartbeat logs only.
- `access.log`: stores access logs.
- `metrics.log`: stores metrics logs.
- `audit.log`: stores audit logs.
- `message.log`: stores message send/receive logs.
- `system.log`: stores system logs.

## 4.2 Storage Strategies for Different Types of Logs

The long-term retention, multi-dimensional complex querying and offline in-depth analysis of log data need to rely on storage systems and tiered storage strategies adapted to their characteristics. Different types of logs differ significantly in data structure, access frequency and business requirements, so differentiated storage solutions need to be formulated specifically:

1. **Heartbeat Logs**
   - Access pattern: mainly "latest state", with almost no need for historical backtracking.
   - Recommendation: no need to store heartbeat details; they can be deleted once message consumption is complete.

2. **Metrics Logs**
   - Access pattern: aggregation by time series, percentile statistics, long-term trend analysis.
   - Recommendation: use **time-series database (TSDB)** storage to obtain efficient downsampling, compression and trend aggregation capabilities.

3. **Access Logs**
   - Access pattern: querying by time range, aggregate statistics by interface/service, error rate analysis, etc.
   - Recommendation: use **columnar / search-oriented analytical storage that supports full-text search and large-scale aggregation**.
   - Note: access logs are usually large in volume but high in value, and are an important basis for performance optimization and fault localization.

4. **Message Logs**
   - Access pattern: retrieval by dimensions such as topic/queue, partition/offset, messageId and eventType, used to troubleshoot backlog, retries, out-of-order delivery and duplicate consumption problems.
   - Recommendation: adopt **analytical storage that supports high write throughput and columnar aggregation** to store structured message metadata; when necessary, keep the original message content in object storage or a compressed repository.
   - Note: message logs usually do not need to be retained as long as audit logs, but they need to be retained for the most recent several hours to several days to support problem backtracking; if the message body has already been retained in the messaging system, only metadata and a summary may be recorded.

5. **Audit Logs**
   - Access pattern: precise queries based on user/resource/time range, with compliance and forensics requirements.
   - Recommendation: use **storage with strong consistency, transaction support and good auditing capabilities** (such as a strongly consistent relational database or a dedicated audit system).
   - Caution: audit logs usually require a long retention period (depending on regulatory requirements), and archiving, partitioning and hot/cold data tiering strategies must be considered.

6. **System Logs**
   - Access pattern: retrieval of runtime environment and associated service status by time range and keyword, mostly used as an auxiliary perspective for troubleshooting access/metrics logs.
   - Recommendation: use **columnar / search-oriented analytical storage that supports full-text search and large-scale aggregation**, which may share the same type of storage as access logs.
   - Note: the system body is in a free format, the original text is placed in `rawBody`, and only stable outer fields are queried structurally; no deep structural parsing is performed.

The overall principles are:

- **Short-term, high-frequency, low-value logs** (such as heartbeats) are handled in a "stream + state" manner, without large-scale detail storage.
- **Logs with medium- and long-term analytical value** (such as access and audit logs) use storage systems that support indexing and complex queries.
- **High-frequency numerical data** (metrics) is preferentially landed in a time-series database to obtain efficient aggregation and compression capabilities.

> This section only constrains the **storage category** and access patterns. The selection of specific storage products (such as a particular TSDB, columnar database or relational database) is an implementation-layer decision and is outside the scope of this specification; it is to be justified by each implementation design document.

# 5 Log Specifications and Related Definitions

## 5.1 Log Format Definition

### 5.1.1 Schema Versioning

To cope with the future evolution of the log structure (such as adding fields, deprecating fields or restructuring), this protocol introduces a **Schema Versioning** mechanism.

- **Version number format**: use `Major.Minor.Patch` semantic versioning (e.g., `1.0.0`).
- **Compatibility principles**:
  - A `Minor` version upgrade (e.g., `1.0.0` -> `1.1.0`) should remain backward compatible, and only new optional fields are allowed.
  - A `Major` version upgrade (e.g., `1.0.0` -> `2.0.0`) may contain breaking changes and requires a corresponding upgrade of the consumer-side parsing logic.
- **Field location**: the version number must exist as the top-level field `schemaVersion` in every `LogRecord`.

### 5.1.2 LogRecord Structure Definition

This specification recommends the use of **structured logs**, uniformly using JSON as the primary format, to facilitate parsing, filtering and replay in subsequent processing stages.

This chapter defines the top-level record structure LogRecord. All log types are encapsulated using this structure. Different log types carry their own specific content structure in the body field.

```typescript
export interface LogRecord {
  /**
   * Log Schema version number.
   * Follows the semantic versioning specification (e.g., "1.0.0").
   */
  schemaVersion: string;

  /**
   * The time when the event actually occurred at the source (generation time).
   * Uses an ISO 8601 string with time zone to maintain readability and consistency.
   */
  timestamp: string;

  /**
   * The time when the event was received or processed by the monitoring system (such as Kafka) (observation time).
   * Uses an ISO 8601 string with time zone to maintain readability and consistency.
   */
  observedTimestamp?: string;

  /**
   * Agent Identity Code
   * The unique identifier of an agent in the ACPs system, which must be globally unique and traceable.
   */
  aic: string;

  /**
   * Unique identifier of the log event, the idempotent deduplication key of a single event (see 5.1.3 for details).
   *
   * - Generated once by the subject producing the log when writing each log line; UUIDv7 is recommended (globally unique without central coordination, and ordered by time).
   * - It is immutable once written at the source, remains unchanged throughout the Forwarder / Kafka / Writer pipeline, and must not be regenerated downstream.
   * - If the source does not provide it, the consumer (Writer) generates it as a fallback using the deterministic content hash of 5.1.3.
   * - The logId of each query view (AccessEventView.logId, MessageEventView.logId, AuditRecordView.logId, etc.) comes from this field.
   */
  logId?: string;

  /**
   * ACPs log type
   * One of the six log types defined by this protocol.
   */
  logType: ACPsLogType;

  /**
   * Globally unique identifier of the link.
   * Uses a 16-byte (128-bit) random number, serialized as a string of 32 hexadecimal characters.
   * A UUID may be used, but without hyphens.
   */
  traceId?: string;

  /**
   * Local identifier of the current span.
   * Uses an 8-byte (64-bit) random number, serialized as a string of 16 hexadecimal characters.
   */
  spanId?: string;

  /**
   * Parent Span ID
   *
   * The parent span identifier of the current span, used to reconstruct the call chain through logs.
   *
   * - The parentSpanId of the root span is null or undefined
   * - A child span must record the spanId of its parent span
   * - Together with traceId and spanId, the call link can be fully traced
   */
  parentSpanId?: string;

  /**
   * correlationId: business-level correlation ID.
   * Used to link multiple logs in a business sense (for example, an order number or task number). Differences from traceId:
   * - traceId is generated by distributed tracing and emphasizes the technical call chain;
   * - correlationId is usually customized by the business system and emphasizes domain/business correlation; it may span multiple traces or exist independently.
   */
  correlationId?: string;

  /**
   * The raw string representation of the log level.
   * Examples: "INFO", "ERROR", "Critical".
   */
  severityText?: string;

  /**
   * Normalized numerical level.
   * Value ranges: 1-4 (TRACE), 5-8 (DEBUG), 9-12 (INFO), 13-16 (WARN), 17-20 (ERROR), 21-24 (FATAL).
   */
  severityNumber?: SeverityNumber;

  /**
   * Log body content.
   * May be any JSON-compatible structure; the specific content depends on the log type.
   */
  body?: AnyValue;

  /**
   * Log source description.
   * Identifies the application or infrastructure that produced this log.
   */
  resource?: Resource;

  /**
   * Additional key-value pair attributes.
   * Used to supplement the contextual information describing the log.
   */
  attributes?: Record<string, AnyValue>;

  /**
   * Data integrity verification information (Digital Signature).
   * Used to ensure that the log has not been tampered with during transmission and to verify the authenticity of the source (non-repudiation).
   * The signature is generated on the Agent side and travels with the log until it is finally stored.
   *
   * Although it is currently mainly used for audit logs, the design supports signing any critical log.
   */
  integrity?: {
    /**
     * Signature algorithm.
     * "EdDSA" (Ed25519) is the first recommendation, "ES256" (ECDSA using P-256 and SHA-256) the second, and "RS256" (RSA Signature with SHA-256) the alternative.
     *
     * Algorithm comparison:
     * | Algorithm | Signature length | Security strength | Speed  | Compatibility           |
     * |--------|----------|-----------------|--------|-------------------------|
     * | EdDSA  | 64 bytes  | 128-bit strength  | Fastest   | Modern systems (SSH/TLS 1.3) |
     * | ES256  | 64 bytes  | 128-bit strength  | Fast     | Widespread (WebAuthn/FIDO2)  |
     * | RS256  | 256 bytes | 112-bit strength  | Slower   | Most widespread (legacy systems)      |
     *
     * Reasons for recommending EdDSA (Ed25519):
     * - Best performance: signing and verification speeds are both better than ECDSA and RSA
     * - Simple implementation: no random number needed, naturally resistant to side-channel attacks, avoiding the ECDSA k-value reuse vulnerability
     * - Compact keys: the public key is only 32 bytes and the private key is only 32 bytes
     * - No patent issues: completely open, with no usage restrictions
     * - Mature ecosystem: natively supported by mainstream languages such as Go/Rust/Node.js/Python
     *
     * This system is a newly built environment with no historical compatibility burden, so EdDSA is the first choice.
     * ES256 serves as the alternative, suitable for scenarios that need to interact with the browser Web Crypto API.
     * RS256 is used only when compatibility with legacy systems is required.
     *
     * The hash algorithm is already implicit in the algorithm name: when signing, a hash is first computed over the data to be signed, and then the hash value is signed asymmetrically.
     * This is the standard practice for digital signatures and needs no additional definition here.
     * @example "EdDSA"
     */
    alg: string;

    /**
     * Key ID (kid), required.
     * Identifies the specific key version or certificate serial number used for signing.
     * Although a certificate is usually bound to an AIC, considering key rotation and multi-version coexistence,
     * the AIC alone cannot uniquely determine the public key required for verification, so kid must be specified explicitly.
     * The recommended value is usually the serial number of the AIC certificate used for signing (the X.509 serialNumber field, an uppercase hexadecimal string).
     *
     * [Source]: After obtaining the certificate from the CA, the Agent parses it directly from the local certificate file:
     *   cert = x509.load_pem_x509_certificate(pem_bytes)
     *   kid  = format(cert.serial_number, "X")   // e.g. "3F8A91B2C4D5E6F7"
     *
     * [Uniqueness guarantee]: The X.509 standard (RFC 5280 §4.1.2.2) requires that the serial number of every certificate
     * issued by the same CA must be unique, so kid can uniquely locate a certificate and its public key globally.
     *
     * [Key rotation]: After an Agent certificate is renewed it obtains a new serial number, and signing with the new
     * certificate's private key automatically carries the new kid; the verifying party can still look up the old public key
     * on the CA side using the old kid, so both new and old logs can be verified without extra version management.
     *
     * During verification, the Consumer uses kid to query the CA service directly for the public key of the corresponding certificate.
     * @example "3F8A91B2C4D5E6F7A8B9C0D1E2F3A4B5"
     */
    kid: string;

    /**
     * Digital signature.
     * A Base64 string after signing the key fields of the log.
     *
     * [Signature scope]:
     * The signature covers the top-level common fields + the entire body object:
     * - timestamp (prevents replay)
     * - aic (prevents source forgery)
     * - logId (prevents the idempotency key from being tampered with to bypass deduplication or create collisions)
     * - traceId, spanId, parentSpanId (prevents link tampering)
     * - correlationId (prevents business correlation from being tampered with)
     * - logType (prevents type confusion)
     * - body (the entire object participates in the signature to prevent content tampering)
     *
     * [Canonicalization rules]:
     * RFC 8785 (JCS - JSON Canonicalization Scheme) is used for deterministic serialization,
     * ensuring that the input is exactly the same at signing and verification time. The main rules include:
     * - Object keys are sorted in ascending order of Unicode code point
     * - Optional fields: skipped when absent, participating in the signature when present
     * - Numbers do not use scientific notation and do not retain redundant decimal places
     * - No whitespace characters are included (no indentation, no line breaks)
     */
    sig: string;
  };
}

/**
 * Type-safe AnyValue type
 *
 * Unlike TypeScript's `any`, AnyValue is a constrained dynamic type:
 * - Type-safe: limited to a union of specific types, checkable at compile time
 * - Serializable: only JSON-serializable values are allowed (excluding functions, Symbols, DOM references, etc.)
 *
 * JSON natively does not support binary types; byte arrays (bytes) should use Base64 encoding when serialized to JSON.
 * For example: Uint8Array([0x01, 0x02, 0x03]) serializes to "AQID".
 */
type AnyValue =
  | string
  | number
  | boolean
  | null
  | Uint8Array
  | AnyValue[]
  | { [key: string]: AnyValue };

/**

 *
 * The values defined here are consistent with the base levels in the OTel specification (the first of each group).
 * OTel provides 4 sub-levels for each base level (such as DEBUG, DEBUG2, DEBUG3, DEBUG4),
 * used to provide fine-grained space when mapping between different log systems.
 */
export enum SeverityNumber {
  UNSPECIFIED = 0,
  TRACE = 1,
  DEBUG = 5,
  INFO = 9,
  WARN = 13,
  ERROR = 17,
  FATAL = 21,
}

/**

 */
export type ACPsLogType =
  | "heartbeat"
  | "access"
  | "metrics"
  | "audit"
  | "message"
  | "system";

/**

  "service.name": string;

  /** Deployment environment name, such as "production", "staging", "development" */

  // --- Host ---
  /** Host name */
  "host.name"?: string;
  /** Host ID */
  "host.id"?: string;
  /** Host architecture, such as "x86_64", "arm64", "amd64" */
  "host.arch"?: string;

  /** Process ID */

  /** Process executable file name */
  "process.executable.name"?: string;
  /** Process command line */
  "process.command_line"?: string;

  // --- Container (K8s/Docker) ---

  "cloud.provider"?: string;

 * Used in various log types such as AccessLog and MessageLog to describe error details.

  code?: number | string;
```

### 5.1.3 Log event idempotency key (logId)

The AMP write pipeline is designed for at-least-once, so the same event may be delivered repeatedly or replayed. To ensure the correctness of deduplication and point queries, this protocol defines the top-level `logId` as the **single-event idempotency key**; it is also the source of the `logId` field in each query view (`AccessEventView.logId`, `MessageEventView.logId`, `AuditRecordView.logId`, etc.).

The essential property an idempotency key needs to satisfy is not "global uniqueness", but rather: **the key remains stable when the same physical event is redelivered**, and **different events are almost impossible to collide**. The specification requires the following:

1. **Generated at the source, generated only once**: `logId` is generated once by the subject producing the log when each log line is written. **UUIDv7** is recommended (the prefix is a millisecond timestamp and the rest are random bits; globally unique without central coordination, and ordered by time, which benefits columnar storage compression and indexing); UUIDv4 is also acceptable. Generation at the source is precisely the source of stability — it guarantees that an event "is tagged only once in its lifetime".
2. **Immutable, must not be regenerated downstream**: once `logId` is written at the source, it remains unchanged throughout the Forwarder, the event stream platform and the Writer. No downstream component may regenerate it, otherwise redelivery would produce a different key and deduplication would immediately fail.
3. **Fallback when absent (content addressing)**: if the source does not provide `logId`, the consumer (Writer) **must** fall back to a deterministic content hash — over the fields in the signature scope (`timestamp`, `aic`, `traceId`, `spanId`, `parentSpanId`, `correlationId`, `logType`, `body`, but **not** including `logId` itself), canonicalized according to RFC 8785 (JCS) and then hashed (such as SHA-256, Base64-encoded). The fallback hash **may only cover immutable source content** and must not include pipeline-appended fields such as `observedTimestamp`, otherwise different deliveries of the same event would compute different keys.
4. **Inherent limitation of the fallback**: a content hash merges "concurrent events whose participating fields are all identical" into one record (for example, two identical requests from the same subject in the same millisecond with no trace context). To avoid such false merging, the source should explicitly provide `logId`. This trade-off is consistent with AMP's overall orientation of at-least-once and "making loss visible rather than pursuing exactly-once".
5. **Do not use narrow field combinations**: a narrow combination such as `hash(aic, timestamp, traceId, spanId)` degenerates to `hash(aic, timestamp)` for concurrent events without a trace and produces collisions and data loss, so it **must not** be used as an idempotency key.

The specific deduplication execution mechanism (deduplication window storage, its relationship with incremental materialized views, etc.) is an implementation detail defined by the implementation design document (see Section 7 of AMP-Design and the various `AMP-API-Design-*` topic documents).

## 5.2 Definition of the Heartbeat Status Format

### 5.2.1 HeartbeatBody Definition

The body structure of the heartbeat log, expressing the liveness status of the agent.

```typescript
export interface HeartbeatBody {
  /**
   * System uptime, in seconds
   * Indicates the cumulative running time from system startup to the present
   * @example 86400
   */
  uptimeSeconds?: number;
}
```

**Signature requirement**: Heartbeat logs usually do not need a signature. If a signature is required, the entire body participates in the signature.

## 5.3 Definition of the Metrics Log Format

### 5.3.1 MetricsBody Definition

The body structure of the metrics log. It mainly contains system load and window summary metrics.

```typescript
export interface MetricsBody {
  /**
   * System uptime, in seconds
   * Indicates the cumulative running time from system startup to the present
   * @example 86400
   */
  uptimeSeconds?: number;

  /**
   * Instantaneous load information, reflecting the current resource usage and queue status.
   * @example { activeTasks: 3, queuedTasks: 1, cpuUsage: 45.6, memoryUsage: 52.1 }
   */
  loadMetrics?: LoadMetrics;

  /**
   * Array of summary metrics based on a certain time interval window. More windows can be added as needed.
   * @example [ { window: "PT1M", requestPerSecond: 95.2, ... } ]
   */
  windowMetrics?: WindowMetrics[];
}

export interface LoadMetrics {
  /**
   * Number of tasks currently being executed.
   * A larger number indicates a busier system.
   * @example 12
   */
  activeTasks: number;

  /**
   * Number of tasks waiting for scheduling or queued.
   * When it is 0, there is no queue and the system can accept new tasks.
   * When it is not 0, some tasks are queued waiting to be processed. In this case, the activeTasks count can express the system's upper load capacity.
   * @example 0
   */
  queuedTasks: number;

  /**
   * Maximum number of tasks allowed to be executed.
   * Used to express the upper limit of the system's processing capacity. It should be a fixed value that does not change over time.
   * @example 20
   */
  maxActiveTasks?: number;

  /**
   * Maximum queue length.
   * Used to express the upper limit of the system's queuing capacity. It should be a fixed value that does not change over time.
   * @example 50
   */
  maxQueuedTasks?: number;

  /**
   * CPU usage, percentage (0-100).
   * Indicates the current resource usage. A higher number indicates greater resource usage.
   * Information such as the number of CPU cores is not collected, to avoid exposing too much information and because it contributes little to expressing the timely load. Only an overall CPU usage metric is needed to facilitate judging the system load.
   * @example 72.8
   */
  cpuUsage?: number;

  /**
   * Memory usage, percentage (0-100).
   * Indicates the current resource usage. A higher number indicates greater resource usage.
   * However, memory may be affected by caching and similar factors, so the usage rate may be very high; after all, memory is meant to be used, so this metric alone does not necessarily reflect the system load.
   * The specific details of memory usage are not collected; only an overall memory usage metric is needed to facilitate judging the system load.
   * @example 68.4
   */
  memoryUsage?: number;

  /**
   * Disk usage, percentage (0-100).

   * - p95: 95% of request latencies are ≤ this value → reflects a "stricter user experience" (covering the slowest 5% of requests, suitable for latency-sensitive scenarios such as payment and real-time interaction);
   * - p99: 99% of request latencies are ≤ this value → reflects the "user experience under extreme conditions" (covering the slowest 1% of requests, avoiding a few anomalies dragging down the overall experience, such as e-commerce order placement or live streaming stutter).

   * - If p90 is high → most users are experiencing latency, and optimization should be prioritized;

   */
  p80LatencyMs?: number;
  p75LatencyMs?: number;
  p50LatencyMs?: number;
```

## 5.4 Definition of the Access Log Format

### 5.4.1 AccessBody Definition

The body structure of the access log, recording the interaction process.

Design notes:

- This structure adopts a "greatest common divisor" design and is compatible with both HTTP and RPC (gRPC, Dubbo, etc.) scenarios.
- For HTTP: method=GET/POST, url=Path
- For RPC: method=MethodName, url=Service/InterfaceName

```typescript
export interface AccessBody {
  /** Request duration (milliseconds) */
  durationMs?: number;
  /** Request */
  request?: {
    /**
     * Request method.
     * - HTTP: verb, such as "GET", "POST".
     * - RPC: method name, such as "GetUser", "PlaceOrder".

    method?: string;

    /**
     * Request resource identifier (raw value, including path parameters).
     * - HTTP: URL Path, such as "/api/v1/users/123".
     * - RPC: fully qualified service/interface name, such as "com.example.UserService".
     */
    url?: string;

    /**
     * Normalized route template, used as a stable endpoint aggregation dimension (combined with method).
     * - HTTP: route template, such as "/api/v1/users/{id}".
     * - RPC: fully qualified method name.
     *
     * It should be filled in by the source while it still holds the framework routing context (this is the only link that can obtain the real template);
     * when the source does not provide it, the collection/write side derives it by performing stable path-parameter normalization on url.
     * Do not directly use the high-cardinality url as an aggregation dimension.
     */
    route?: string;

    /**
     * Request headers or metadata.
     * - HTTP: Headers.
     * - RPC: Metadata / Attachments.
     */
    headers?: Record<string, string>;

    /** Request body size (bytes) */
    bodySizeBytes?: number;
  };
  /** Response */
  response?: {
    /**
     * Response status code.
     * - HTTP: 200, 404, 500.
     * - RPC: 0 (OK), 5 (NotFound), etc.; it is recommended to map them uniformly or retain the original values.
     */
    statusCode?: number;

    /** Response headers or metadata */
    headers?: Record<string, string>;

    /** Response body size (bytes) */
    bodySizeBytes?: number;
  };
  /**
   * Caller information (Caller).

   * The value of explicitly recording caller information:
   * 1. Pre-aggregation: the service topology graph (A -> B) can be computed in real time without joining Trace records.
   * 2. Sampling resistance: even if upstream Trace data is sampled away, the current log still retains complete peer information.
   * 3. Fast attribution: during operations troubleshooting, one can directly see in the log who initiated the call, without jumping to the Trace system.
   */
  caller?: {
    /** Agent Identity Code (AIC) of the caller, used for identity recognition and security auditing */
    aic?: string;

    serviceName?: string;
    /** IP address of the caller */
    ip?: string;

    /** Service name of the callee, such as "payment-service" */

    ip?: string;
```

### 5.4.2 Sampling Strategy

The data volume of access logs is usually enormous, and full collection may incur excessively high storage and processing costs. It is recommended to implement a sampling strategy on the Agent side or the Gateway side:

1.  **Probabilistic Sampling**:
    - Simple and straightforward, for example collecting only 10% of the traffic.
    - Drawback: low-frequency but important error requests may be missed.

2.  **Priority-based Sampling**:
    - **Mandatory collection**: all `ERROR`-level logs, slow requests whose duration exceeds a threshold (such as > 1s), and requests from specific VIP users.
    - **Random sampling**: randomly sample 1% ~ 10% of normal `INFO`-level requests.

3.  **Head sampling vs tail sampling**:
    - **Head Sampling**: whether to sample is decided at the start of the request (usually based on the TraceID). The advantage is high performance; the drawback is that no decision can be made based on the request result (such as whether an error occurred).
    - **Tail Sampling**: after the request completes, whether to retain it is decided according to the result. The advantage is that errors and slow requests can be retained precisely; the drawback is that the logs of the entire request lifecycle must be buffered, resulting in high memory overhead.
    - **Recommendation**: adopt a hybrid mode of "head sampling + mandatory retention of key characteristics" on the Agent side; tail sampling may be implemented on a centralized collection side (such as the OpenTelemetry Collector).

## 5.5 Definition of the Message Log Format

### 5.5.1 MessageBody Definition

The body structure of the message log, used to describe a single send/receive or settlement operation in a message-driven architecture. It is compatible with the semantics of common messaging middleware such as Kafka and RabbitMQ, and is aligned with the OpenTelemetry Messaging semantic conventions.

Design points: each message log precisely describes **one** lifecycle boundary event (send, receive, or a particular kind of settlement) through `eventType`. The send, receive and acknowledgement of the same message are **multiple independent logs** (each with its own independent top-level `logId`, merged into a single lifecycle at the query layer through the same `messageId` / `correlationId`), and "received and acknowledged" is never expressed in one log. In this way, every statistical count can unambiguously correspond to one event type. The message "flow direction" (send/receive) is no longer a source field, but is derived from `eventType`.

```typescript
export interface MessageBody {
  /**
   * Message lifecycle boundary event type.
   * Each message log precisely describes ONE operation; one "receive" and the subsequent "acknowledgement" are two independent logs.
   *
   * - send         the producer sends/publishes a message
   * - receive      the consumer obtains/processes a message (both pull and push fall into this category)
   * - ack          settlement: acknowledged successfully
   * - nack         settlement: negatively acknowledged, usually returned to the queue
   * - reject       settlement: rejected and discarded
   * - timeout      settlement: processing or consumption lock timed out
   * - dead_letter  settlement: entered the dead letter queue
   */
  eventType:
    | "send"
    | "receive"
    | "ack"
    | "nack"
    | "reject"
    | "timeout"
    | "dead_letter";

  /**
   * Native operation name of the system (optional), used only for fidelity and troubleshooting, and not participating in standard counting.
   * @example "publish"
   * @example "poll"
   * @example "basic.ack"
   */
  operationName?: string;

  /**
   * Message system type
   * e.g., "kafka", "rabbitmq", "activemq", "rocketmq"
   */
  system: string;
  /**
   * Message destination information
   * Corresponds to a Kafka Topic, or a RabbitMQ Exchange/Queue
   */
  destination: {
    /**
     * Destination name
     * Kafka: Topic Name
     * RabbitMQ: Exchange Name (publish) or Queue Name (consume)
     */
    name: string;
    /**
     * Destination type
     * e.g., "topic", "queue", "exchange"
     */
    kind?: "topic" | "queue" | "exchange";
    /**
     * Virtual host (RabbitMQ specific)
     * Defaults to "/"
     */
    virtualHost?: string;
  };
  /**
   * Consumer group name (filled in for consumer-side events).
   * @example "indexer"
   */
  consumerGroupName?: string;
  /**
   * Subscription name (filled in for consumer-side events).
   * @example "subscription-a"
   */
  subscriptionName?: string;
  /**
   * Message routing information
   */
  routing?: {
    /**
     * Routing key (RabbitMQ) or Message Key (Kafka)
     * Used to determine which partition or queue the message is distributed to
     */
    key?: string;
    /**
     * Partition identifier. A string is used for compatibility with non-Kafka systems, and to distinguish "no partition concept" (field omitted) from "partition 0".
     * @example "1"
     */
    partition?: string;
    /**
     * Message offset (Kafka specific)
     */
    offset?: number;
  };
  /** Unique message identifier ID */
  messageId?: string;
  /** Message body size (bytes) */
  payloadSizeBytes?: number;
  /**
   * Number of delivery attempts (consumer side). 1 means the first delivery, >1 means redelivery; meaningful only for receive and settlement-type events.
   */
  deliveryAttempt?: number;
  /**
   * Supplementary settlement information, filled in only for settlement-type events (eventType is ack/nack/reject/timeout/dead_letter).
   * The settlement "result" is already expressed by eventType; only the latency and reason are supplemented here, and the status field is not repeated.
   */
  settlement?: {
    /** Time elapsed from receive to this settlement (ms). */
    latencyMs?: number;
    /** Settlement reason (the specific reason for nack/reject/dead_letter/timeout). */
    reason?: string;
  };
  /** Error information (if the operation failed) */
  error?: ErrorInfo;
  /** Extended attributes */
  attributes?: Record<string, AnyValue>;
}
```

**Signature requirement**: Message logs usually do not need a signature. If a signature is required, the entire body participates in the signature.

### 5.6.2 Tamper-Proof Methods for Audit Logs

To ensure the integrity and non-repudiation of audit logs across the entire link from **generation (Agent)** to **storage (Database)**, this protocol recommends a dual protection mechanism of "source-side signing + storage-side chained verification".

#### 5.6.2.1 Transport Tamper-Proofing: Source-Side Digital Signature

After logs are generated and pass through transport components such as Kafka/Fluent Bit, there may be a risk of man-in-the-middle tampering. By embedding a source-side digital signature in the log, the following can be ensured:

- **Integrity**: the log content has not been tampered with.
- **Non-repudiation**: the log was indeed produced by the Agent corresponding to that AIC.

**Workflow**:

1.  **Signature generation (Agent side)**:
    - When generating an audit log, the agent signs the core content of the log using its private key (Private Key).
    - The signature scope includes the top-level common fields (`timestamp`, `aic`, `logId`, `traceId`, `spanId`, `parentSpanId`, `correlationId`, `logType`) as well as the entire `body` object.
    - The signature result is stored in the top-level `LogRecord.integrity.sig` field.

2.  **Transport protection**:
    - Even if the log is maliciously tampered with while passing through middleware such as Kafka or Fluent Bit (for example `result.status` is modified), the consuming side will detect the inconsistency during signature verification, because the middleware cannot forge the corresponding signature.

3.  **Signature verification and storage (Consumer/Storage side)**:
    - When consuming logs, the audit log service uses `integrity.kid` (the certificate serial number) to query the CA service for the public key (Public Key) of the corresponding certificate.
    - Verify whether `integrity.sig` is valid.
    - Only logs that pass signature verification are marked as "trusted" and written to the audit database; logs that fail verification should trigger a severe alert.

#### 5.6.2.2 Storage Tamper-Proofing: Chained Hash

After logs are written to the database, there may still be a risk of a DBA or an internal attacker tampering with historical records. To satisfy the immutability property, it is recommended to implement a lightweight "chained storage" on top of a relational database:

- Each audit log should contain the **hash value of the previous log (Previous Hash)** and the **hash value of the current log (Current Hash)**.
- `Current Hash = Hash(key fields of the current log + Previous Hash)`.
- In this way, the integrity of a single record can be verified, and a hash chain is formed to prevent historical data from being tampered with or deleted.

# 6 AMP API Definition

## 6.1 General Specification for Query APIs

An AMP Provider provides HTTP query interfaces based on the stable read model after AMP logs are written to storage. The AMP API does not accept logs reported directly by Agents, nor does it redefine the Snapshot / Changes / Webhook synchronization semantics of DSP; when replicating the stable read model across systems, this should be accomplished through DSP or through the synchronization sub-protocols specifically declared in this specification.

The unified base path of the AMP API is denoted by `{AMP_BASE_URL}`, configured by the deployer (for example `/amp/v1`). The API prefixes corresponding to the six log types are as follows:

| Log type  | API prefix                    | Minimum capability set                                  | Optional Profile                        |
| --------- | ----------------------------- | ------------------------------------------------------- | --------------------------------------- |
| heartbeat | `{AMP_BASE_URL}/heartbeat`    | single-AIC liveness query, batch liveness query, summary | alive set snapshot + delta sync        |
| metrics   | `{AMP_BASE_URL}/metrics`      | snapshot query, series query                            | rankings, SLO evaluate, capacity        |
| access    | `{AMP_BASE_URL}/access`       | events query, operations aggregation                    | errors, slow requests, trace, topology  |
| message   | `{AMP_BASE_URL}/message`      | events, lifecycles, deadletters                         | destination state, throughput           |
| audit     | `{AMP_BASE_URL}/audit`        | records, record detail, summary                         | export, integrity verify, chain anchors |
| system    | `{AMP_BASE_URL}/system`       | system events query                                     | incidents, trend, component attribution |

### 6.1.1 Authentication, Transport and Error Response

- The recommended authentication method is `mTLS`, with the certificate bound to the calling principal. Agent-type principals should be bound to an AIC; non-Agent Consumers such as platforms, operations consoles, regulatory ends and billing systems may be bound to an organization, tenant, role or service account.
- When deployed on a controlled intranet, Bearer Token, JWT or gateway authentication may be layered on top.
- All AMP APIs use `application/json` by default.
- Error responses follow RFC 9457 Problem Details and must carry an AMP error code.
- All time fields use ISO 8601 strings with time zone.

Common HTTP status semantics (shared by the six API groups; each group does not define them separately):

- When authentication information is missing or invalid, `401 AMP_UNAUTHENTICATED` is returned; when the principal is authenticated but not authorized to access this type of monitoring data, `403 AMP_ACCESS_DENIED` is returned.
- When the call rate exceeds the Provider quota or the caller is rate-limited, `429 AMP_RATE_LIMITED` is returned, and `Retry-After` may be used to indicate the retry interval.
- An unclassified internal exception in the Provider returns `500 AMP_INTERNAL_ERROR`; for attributable cases such as dependency unavailability or significant read-model lag, a more specific `503` error code should be used preferentially (see the specification of each group).

```typescript
/**
```

General query rules:

1. For list queries, aggregation queries and export queries on the append-only event stream, the caller must provide a bounded `timeRange`; if it is missing, `400 AMP_INVALID_TIME_RANGE` is returned.
2. `filter`, `sort`, the aggregation `groupBy`, and the fields covered by `keyword` must all appear in the whitelist declared by the corresponding API group; fields that are not declared must not be silently supported.
3. For resources that are naturally appended in time order, if the caller does not provide `sort`, the default sort is `timestamp desc`; if this default does not apply to a certain API group, it must be declared separately in that group's specification.
4. `keyword` is a restricted search entry point and is not equivalent to full-text search over `raw_log`.
5. When paginating with `page.cursor`, the query parameters and sort conditions other than `cursor` must be exactly the same as those of the previous page; if they are inconsistent, the Provider should return `400 AMP_CURSOR_INVALID`.
6. `includeRawLog` is disabled by default; the Provider should return the raw log or a raw body digest only when the API group explicitly declares support for it.

### 6.1.3 Complex Filter Model

```typescript
/**
 * Composite filter, supporting nesting at any level, sharing the same set of logical semantics as the ADP DiscoveryFilter.
 * The conditions and groups at the same level are combined according to logic; with groups, compound conditions such as (A and B) or C can be expressed.
 */
export interface AMPFilter {
  /** Filter conditions of the current level. They are combined with the child condition groups in groups according to the logical relationship specified by logic. */
  conditions?: AMPFilterCondition[];
  /** Nested child condition groups of the current level; each child group may have its own independent logic. */
  groups?: AMPFilter[];
  /** Logical relationship between the conditions and child groups of the current level. "not" means negating the overall result of the current level. Defaults to "and". */
  logic?: "and" | "or" | "not";
}

/** A single filter condition, whose semantics are "the field and the value satisfy the relationship defined by the operator op". */
export interface AMPFilterCondition {
  /** Field path, using dot notation for nesting */
  field: string;
  /** Match operator */
  op: AMPFilterOperator;
  /** Match value; the concrete form is determined by op and the field type */
  value?: AnyValue;
}

/**
 * The complete set of filter operators. String-type operators are case-insensitive by default, and the suffix `Cs` (Case-sensitive) is their case-sensitive variant.
 * If a field or the backend does not support a certain operator, 422 AMP_UNSUPPORTED_OPERATOR must be returned, and it must not silently degrade to other semantics.
 */
export type AMPFilterOperator =
  // Equality and existence
  | "eq" // equal to
  | "ne" // not equal to
  | "exists" // whether the field exists (value is true / false)
  // Numeric / time comparison
  | "gt" // greater than
  | "gte" // greater than or equal to
  | "lt" // less than
  | "lte" // less than or equal to
  | "between" // closed interval [a, b]; value is a two-element array
  // Set membership
  | "in" // the value belongs to the given set
  | "nin" // the value does not belong to the given set
  // String matching (case-insensitive)
  | "contains" // contains the substring
  | "notContains" // does not contain the substring
  | "startsWith" // prefix match
  | "endsWith" // suffix match
  // String matching (case-sensitive variants, semantics as above)
  | "eqCs"
  | "neCs"
  | "inCs"
  | "ninCs"
  | "containsCs"
  | "notContainsCs"
  | "startsWithCs"
  | "endsWithCs"
  // Array element matching (when the field value is an array)
  | "anyOf" // has an intersection with the given set
  | "allOf" // contains all elements of the given set
  | "noneOf" // has no intersection with the given set
  // Array length
  | "size" // length equals
  | "sizeGt" // length greater than
  | "sizeGte" // length greater than or equal to
  | "sizeLt" // length less than
  | "sizeLte" // length less than or equal to
  // Object key existence (when the field value is an object)
  | "hasKey" // contains the specified key
  | "hasNoKey" // does not contain the specified key
  | "hasAnyKey" // contains any key of the given key set
  | "hasAllKeys"; // contains all keys of the given key set
```

`AMPFilter` maintains the same set of logical semantics as the ADP `DiscoveryFilter`: `and` means all conditions/subgroups are satisfied, `or` means at least one is satisfied, and `not` means the overall result of the current level is negated. String operators are case-insensitive by default; the suffix `Cs` denotes the case-sensitive variant. If an API group or backend storage does not support a field path or operator in the request, the Provider must return `422 AMP_UNSUPPORTED_FIELD` or `422 AMP_UNSUPPORTED_OPERATOR`, and must not silently degrade to other semantics.

### 6.1.4 Result Freshness and Consistency

The AMP read model is not a transactionally synchronized view; query responses must expose the true event-time watermark.

| Log type  | Typical visibility latency | `dataFreshnessAt` definition                                        | Recommended threshold for `AMP_READ_MODEL_LAGGING` |
| --------- | -------------------------- | ------------------------------------------------------------------- | -------------------------------------------------- |
| heartbeat | < 1 second                 | event-time watermark already consumed by the heartbeat writer       | 5,000 ms                                           |
| metrics   | 5~30 seconds               | event-time watermark persisted and aggregatable in the metrics read model | 150,000 ms                                   |
| access    | 5~60 seconds               | event-time watermark landed in the database and queryable in the access read model | 300,000 ms                          |
| message   | 5~60 seconds               | event-time watermark landed in the database and queryable in the message read model | 300,000 ms                         |
| audit     | 1~10 seconds (signature verification overhead) | event-time watermark signature-verified and committed in the audit read model | 60,000 ms                     |
| system    | 5~60 seconds               | event-time watermark indexed and visible in the system read model   | 300,000 ms                                         |

The freshness requirements in this section apply to all responses carrying `AMPResponseMeta`, including lists, aggregations, and single-resource reads declared by each group's specification as a `{ data, meta }` envelope (such as Heartbeat's `/liveness/{aic}` and `/summary`). If an endpoint returns a bare resource according to its group specification (without `meta`, such as `GET /traces/{traceId}` or `GET /records/{auditId}`), that group's specification must declare how its freshness is exposed (for example through a response header or a field of its own); otherwise it is considered outside the scope of this requirement.

Any query response (carrying `meta`) must give the true read-model event-time watermark in `meta.dataFreshnessAt`, and expose an estimate of `now() - dataFreshnessAt` in `meta.ingestionLagMs`. When `ingestionLagMs` exceeds the threshold for the corresponding type, the Provider must return `503 AMP_READ_MODEL_LAGGING`, or return `200` with `meta.partial = true` set. If some aggregate fields are computed from only part of the samples, the Provider must mark them in `meta.partialDataFields` and `meta.sampleCoverage`.

If the query time range exceeds the retention window of the corresponding read model, the Provider must return `422 AMP_OUT_OF_RETENTION`.

## 6.2 Heartbeat API Specification

The Heartbeat API prefix is `{AMP_BASE_URL}/heartbeat`, used to query the current liveness of a subject. Heartbeat expresses only signs of liveness, not health, readiness or maintenance.

Cross-system replication of the Heartbeat alive set adopts the **alive-delta synchronization sub-protocol** (Sync Profile) declared in this specification: the Consumer first completes a full bootstrap through `/sync/snapshot`, and then subscribes to the incremental delta log to keep catching up. At the transport layer, this sub-protocol **standardizes on Kafka** as the delta log; the `kafkaTopic` and `shardCount` exposed by `/sync/info`, together with the sharded `seq` of the `AliveDeltaEnvelope`, constitute its wire contract. This is a deliberate transport coupling, used to guarantee interoperability between different Providers and Consumers; deployments that do not provide Kafka may leave the Sync Profile disabled (`/sync/*` returns `404 AMP_HEARTBEAT_SYNC_DISABLED`), but once it is enabled, the Kafka transport and sharding semantics defined in this section must be followed. Core query capabilities (liveness, summary, etc.) do not depend on this sub-protocol.

### 6.2.1 Resource Model

```typescript

 * The liveness view of a subject (AIC). liveness expresses only "whether it is still

  sourceTimestamp?: string;

  silenceDurationSeconds: number;
}

  lastSeenAt: string;
  /** The current silence duration (seconds). */
  silenceDurationSeconds: number;
}

/** Silence ranking query request (POST /silence/top). */
export interface HeartbeatSilenceTopRequest {
  /** Return the top N subjects with the longest silence, subject to the Provider limit. */
  topN?: number;
  /** Return only subjects whose silence duration is ≥ this value (seconds). */
  minSilenceSeconds?: number;
  /** Return only subjects whose silence duration is ≤ this value (seconds). */
  maxSilenceSeconds?: number;
  /** Whether to count only subjects currently in the silent state. */
  onlySilent?: boolean;
}

/** Liveness summary view (GET /summary), giving the overall alive/silent distribution. */
export interface HeartbeatSummaryView {
  /** Total number of known subjects (those that have reported a heartbeat and have not yet been evicted). */
  totalKnown: number;
  /** The number of currently alive subjects. */
  aliveCount: number;
  /** The number of currently silent subjects. */
  silentCount: number;
  /**
   * Cumulative silence duration buckets (cumulative, "le" semantics): leSeconds is the
   * upper bound of the bucket (seconds), and count is the cumulative number of currently
   * known subjects with silenceDurationSeconds ≤ leSeconds (including subjects that fall
   * into smaller buckets). Therefore count is monotonically non-decreasing as leSeconds
   * increases; when the count of a single interval (non-cumulative) is needed, the caller
   * takes the difference between adjacent buckets.
   */
  silenceBuckets?: Array<{ leSeconds: number; count: number }>;
  /** Whether this is a partial result (for example, some shards did not respond). */
  partial?: boolean;
  /** The number of shards that responded successfully. */
  respondedShardCount?: number;
  /** The total number of shards. */
  totalShardCount?: number;

 * Metadata of a heartbeat response: on top of the common AMPResponseMeta (freshness,
 * pagination, partial results, etc.), it appends the time basis and thresholds used for
 * this liveness determination.
 * All Heartbeat query endpoints (including the two single-resource reads /liveness/{aic}
 * and /summary) uniformly use this type as the response meta, so common freshness fields
 * such as dataFreshnessAt / ingestionLagMs are likewise required on heartbeat queries
 * (see 6.1.4).
 */
export interface HeartbeatResponseMetaExt extends AMPResponseMeta {
  /** The server time on which this liveness determination was based. */
  evaluatedAt: string;
  /** The silence threshold for determining silent (seconds): silence beyond this value is treated as silent. */
  silenceThresholdSeconds: number;
  /** The eviction threshold (seconds): after silence exceeds this value the subject is removed from the known set. */
  evictAfterSeconds: number;
}

/** alive set synchronization entry, describing the minimal state of one currently alive subject. */
export interface AliveSetEntry {
  /** Agent identity code. */
  aic: string;
  /** The most recent heartbeat time. */
  lastSeenAt: string;
  /** The time at which the heartbeat was produced on the source side. */
  sourceTimestamp?: string;
}

/**
 * alive set incremental synchronization envelope (one line in the NDJSON stream), used to
 * replicate the "current alive set" across systems.
 * A remote end maintains a replica of the alive set by means of a full snapshot plus
 * subsequent incremental events (enter/refresh/leave).
 */
export interface AliveDeltaEnvelope {
  /** The shard it belongs to. */
  shard: string;
  /**
   * A monotonically increasing sequence number within the shard, used for resumable
   * transfer and deduplication; its value is the string encoding of a decimal non-negative
   * integer.
   * It is ordered only within the same shard. Comparing seq (for example, the resumable
   * transfer check seq > cutover) must be done numerically, never by string lexicographic order.
   */
  seq: string;
  /** Envelope type, fixed as "amp-alive-delta". */
  type: "amp-alive-delta";
  /**
   * Synchronization object ID (note: not a per-event unique ID), fixed as urn:amp:alive:<aic>.
   * All events of the same subject share the same id and are ordered by version; the
   * Consumer converges idempotently by (id, version).
   */
  id: string;
  /**
   * Object version number, with the same value as seq (a decimal integer string).
   * Only a larger version is kept for the same id; comparison must be performed numerically.
   *
   * Why seq within a shard can directly serve as the object version: events for the same
   * aic are always routed to the same shard (partition = shard index, sharded by aic), so
   * all events within the lifetime of one id (urn:amp:alive:<aic>) fall in the same shard and
   * are totally ordered by that shard's seq, and monotonic seq means monotonic version.
   * The two fields coexist with separate duties: seq is the shard-level replay/resumable
   * transfer/deduplication cursor (used when a consumer catches up along the delta log),
   * while version lets a generic upsert consumer that converges only by (id, version) merge
   * idempotently without needing to understand sharding.
   */
  version: string;
  /** Operation: upsert=add/update the entry; delete=remove the entry. */
  op: "upsert" | "delete";
  /** Event semantics: snapshot=snapshot entry; enter_alive=newly entering alive; refresh_alive=alive refresh; leave_alive=leaving alive. */
  kind: "snapshot" | "enter_alive" | "refresh_alive" | "leave_alive";
  /** The associated alive entry data (may be omitted when op=delete). */
  payload?: AliveSetEntry;
}

/**
 * alive set synchronization parameters (GET /sync/info response).
 * Describes the transport contract of the alive-delta synchronization subprotocol: the
 * incremental log topic, the number of shards, the compaction emission interval, the
 * retention window, and the current publication watermark of each shard. The Consumer uses
 * this to locate the delta log and complete bootstrapping and catch-up.
 */
export interface HeartbeatSyncInfo {
  /** Synchronization envelope type, fixed as "amp-alive-delta". */
  type: "amp-alive-delta";
  /** Schema version of the synchronization subprotocol. */
  schemaVersion: string;
  /** Content type of the snapshot stream, fixed as "application/x-ndjson". */
  snapshotContentType: "application/x-ndjson";
  /** The name of the Kafka topic carrying alive incremental events. */
  kafkaTopic: string;
  /** The number of shards; the number of Kafka partitions matches it, and partition = shard index. */
  shardCount: number;
  /** The compaction emission interval for refresh_alive events (seconds). */
  refreshEmitIntervalSeconds: number;
  /** The minimum retention duration of the delta log (hours), used to protect the Consumer's replay window. */
  deltaRetentionHours: number;
  /** The currently contiguously published high-watermark sequence number of each shard (shard -> seq). */
  currentPublishedSeqByShard: Record<string, string>;
}

/**
 * First-line metadata of the alive snapshot stream (the first line of the
 * GET /sync/snapshot response).
 * Each subsequent line is an AliveDeltaEnvelope with kind = "snapshot".
 * The Consumer uses cutoverSeqByShard to determine the starting position for incremental
 * catch-up on the delta log.
 */
export interface AliveSnapshotMeta {
  /** Record type, fixed as "snapshot-meta". */
  recordType: "snapshot-meta";
  /** Synchronization envelope type, fixed as "amp-alive-delta". */
  type: "amp-alive-delta";
  /** The cutover sequence number of each shard for this snapshot (shard -> seq): incremental catch-up starts after this sequence number. */
  cutoverSeqByShard: Record<string, string>;
  /** The time the snapshot was generated. */
  generatedAt: string;
}
```

### 6.2.2 Filterable Fields

| Field Path               | Operators                           | Description                                              |
| ------------------------ | ----------------------------------- | -------------------------------------------------------- |
| `aic`                    | `eq`, `in`                          | Literal match on AIC                                     |
| `isAlive`                | `eq`                                | Liveness determination under the server's current time   |
| `livenessState`          | `eq`                                | A state computed on the fly by the query layer           |
| `silenceDurationSeconds` | `gt`, `gte`, `lt`, `lte`, `between` | The current silence duration                             |

### 6.2.3 Endpoints

| Method | Path              | Request Body / Parameters    | Response Body                                                                        | Profile   |
| ------ | ----------------- | ---------------------------- | ------------------------------------------------------------------------------------ | --------- |
| GET    | `/liveness/{aic}` | path `aic`                   | `{ data: HeartbeatLivenessView; meta: HeartbeatResponseMetaExt }`                     | Core      |
| POST   | `/liveness/query` | `AMPQueryRequest`            | `AMPQueryResponse<HeartbeatLivenessView>` (`meta` is `HeartbeatResponseMetaExt`)      | Core      |
| POST   | `/silence/top`    | `HeartbeatSilenceTopRequest` | `AMPQueryResponse<HeartbeatSilenceRankItem>` (`meta` is `HeartbeatResponseMetaExt`)   | Analytics |
| GET    | `/summary`        | none                         | `{ data: HeartbeatSummaryView; meta: HeartbeatResponseMetaExt }`                      | Core      |
| GET    | `/sync/info`      | none                         | `HeartbeatSyncInfo`                                                                   | Sync      |
| GET    | `/sync/snapshot`  | none                         | `application/x-ndjson` alive snapshot                                                 | Sync      |

The `/sync/info` response body is `HeartbeatSyncInfo` (see 6.2.1). `/sync/snapshot` is an `application/x-ndjson` stream: the first line is `AliveSnapshotMeta` (see 6.2.1), and each subsequent line is an `AliveDeltaEnvelope` with `kind = "snapshot"`.

Response envelope convention: the two single-resource read endpoints of Heartbeat (`/liveness/{aic}`, `/summary`) deliberately use the `{ data, meta }` envelope rather than a bare resource, so that they carry freshness fields such as `meta.dataFreshnessAt` consistently with list/aggregate endpoints (see 6.1.4). The `meta` type of these four query endpoints is uniformly `HeartbeatResponseMetaExt` (which extends `AMPResponseMeta`). `/sync/*` is not a read-model query; it keeps the response bodies defined for it respectively and does not apply that envelope.

### 6.2.4 Query Constraints and Error Codes

- When `GET /liveness/{aic}` misses the current source of truth, it returns `404 AMP_HEARTBEAT_AIC_UNKNOWN` and must not return a placeholder object with `isAlive=false`.
- If `POST /liveness/query` has no `aic` filter, it must provide a pushdown-able selective filter or a cursor; otherwise it returns `400 AMP_QUERY_REQUIRES_SELECTIVE_FILTER`.
- The `topN` of `POST /silence/top` must be limited by the Provider limit; when the silence range is invalid, it returns `400 AMP_HEARTBEAT_SILENCE_RANGE_INVALID`.
- When snapshot + delta sync is not enabled, `/sync/*` returns `404 AMP_HEARTBEAT_SYNC_DISABLED`.

Heartbeat-specific error codes (in addition to the common error codes in 6.1.5):

| Error Code                            | HTTP | Description                                                                                          |
| ------------------------------------- | ---- | ---------------------------------------------------------------------------------------------------- |
| `AMP_QUERY_REQUIRES_SELECTIVE_FILTER` | 400  | `liveness/query` provided no pushdown-able selective filter and carried no cursor                     |
| `AMP_HEARTBEAT_SILENCE_RANGE_INVALID` | 400  | The silence range parameters of `silence/top` are invalid                                             |
| `AMP_HEARTBEAT_SYNC_VIEW_UNSUPPORTED` | 400  | A synchronization view type not supported by the current deployment was requested                     |
| `AMP_HEARTBEAT_AIC_UNKNOWN`           | 404  | A single-AIC query missed the current source of truth                                                 |
| `AMP_HEARTBEAT_SYNC_DISABLED`         | 404  | The current deployment has not enabled snapshot + delta sync                                          |
| `AMP_HEARTBEAT_SNAPSHOT_UNAVAILABLE`  | 503  | Snapshot export is temporarily unavailable (for example, the source of truth is unreachable or the export is rate-limited) |
| `AMP_HEARTBEAT_DELTA_LOG_UNHEALTHY`   | 503  | Incremental log publication lags significantly or is unreachable, so incremental freshness cannot be guaranteed |

### 6.4.4 Query Constraints and Error Codes

- Except for `GET /traces/{traceId}`, all access query interfaces must carry `timeRange`.
- The `endpoint` aggregation dimension is uniformly mapped to `request.method + request.route`; the original `request.url` must not be used as a stable aggregation dimension.
- `traces/query` and `topology/query` support only materialized fields; encountering an unmaterialized field must return `AMP_UNSUPPORTED_FIELD`.
- `includeRawLog=true` is effective only when the deployment enables raw log storage.
- **Error event determination** (used for the `errorCount` and `errorRate` of `AccessOperationSummary` / `AccessTopologyEdge` and for `errors/attribution`): `response.statusCode >= 500` **or** a non-empty `error.code` is regarded as an error; `4xx` is not counted as an error by default (deployments may adjust the lower bound of the status code). The same criterion must stay consistent across operations, topology, and errors.
- The **`aic` dimension** refers to **the principal that produced the access log** (that is, `LogRecord.aic`), neither `caller.aic` nor `callee.aic`; aggregating by `aic` mixes the two perspectives of that principal as caller and as callee. When the call direction needs to be distinguished, use `caller.*` / `callee.*` instead.
- **Time alignment of `topology/query`**: the topology read model is maintained at a fixed bucket granularity (implementation recommendation: 5 minutes). `timeRange` is expanded outward to bucket boundaries and rounded (start rounded down, end rounded up), and the returned `bucket` is the bucket start; callers should not expect topology to be split precisely at sub-bucket granularity.
- **Freshness and truncation of `GET /traces/{traceId}`** (a bare resource response, satisfying the declaration requirement of 6.1.4 for endpoints without `meta`): read model freshness is exposed through the response headers `AMP-Data-Freshness-At` (ISO 8601) and `AMP-Ingestion-Lag-Ms`; the number of spans returned for a single trace is bounded by the Provider limit, and when the limit is exceeded the result is truncated and the response header `AMP-Trace-Truncated: true` is set.

| Error code | HTTP | Description |
| --- | --- | --- |
| `AMP_TRACE_NOT_FOUND` | 404 | The specified `traceId` is not within the current retention range |
| `AMP_TOPOLOGY_GROUPBY_INVALID` | 422 | The `groupBy` value of `topology/query` is not supported |
| `AMP_ATTRIBUTION_GROUPBY_INVALID` | 422 | The aggregation dimension of `errors/attribution` is not supported |

### 6.5.4 Query Constraints and Error Codes

- Except for `GET /lifecycles/{messageId}`, all message query interfaces must carry a `timeRange` or an equivalent window.
- Time window semantics: `lifecycles/query` interprets `timeRange` by `lastSeenAt`, and `deadletters/query` interprets it by `deadLetteredAt`; `destinations/query` treats `timeRange.end` as the as-of time and `timeRange.start` as the lower bound of snapshot freshness — within the window the latest state snapshot of each destination is taken, and when no usable snapshot exists in the window, `503 AMP_MESSAGE_STATE_SNAPSHOT_UNAVAILABLE` is returned.
- `lifecycles/query` must give at least `messageId`, `lifecycleKey`, `correlationId`, `traceId`, or a sufficiently narrowing constraint such as `system + destination.name + timeRange`.
- duplicate / unacked are preset filter semantics of `lifecycles/query`; no separate endpoints are defined for them.
- `destinations/query` must read destination state snapshots; the produced-consumed difference must not be used to fake the true backlog value.
- `destinations/throughput` expresses only activity trends such as produced / consumed / ack / retry / dead-letter, and does not serve queries of current state fields.
- Freshness exposure of bare-resource endpoints (satisfying the declaration requirement of 6.1.4 for endpoints without `meta`): `GET /lifecycles/{messageId}` and `POST /destinations/throughput` return a bare resource (without `meta`), whose read-model freshness is exposed through the response headers `AMP-Data-Freshness-At` (ISO 8601) and `AMP-Ingestion-Lag-Ms`; when the lag exceeds the message-type threshold, `503 AMP_READ_MODEL_LAGGING` may likewise be returned.

Message-specific error codes (in addition to the common error codes of 6.1.5):

| Error code                               | HTTP | Description                                                                                      |
| ---------------------------------------- | ---- | ------------------------------------------------------------------------------------------------ |
| `AMP_MESSAGE_LIFECYCLE_KEY_REQUIRED`     | 422  | The lifecycle query did not give a sufficiently narrowing aggregation constraint                 |
| `AMP_MESSAGE_LIFECYCLE_AMBIGUOUS`        | 422  | A query by `messageId` matched multiple lifecycles; the destination identity must be supplied     |
| `AMP_MESSAGE_GROUPBY_INVALID`            | 422  | The destination aggregation dimension is not supported                                           |
| `AMP_MESSAGE_DESTINATION_REQUIRED`       | 422  | The throughput query is missing the required destination parameter                               |
| `AMP_MESSAGE_STATE_SNAPSHOT_UNAVAILABLE` | 503  | The destination current state snapshot is not enabled or is severely expired                     |

## 6.6 Audit API Specification

The Audit API prefix is `{AMP_BASE_URL}/audit`, used to query audit records, aggregate statistics, export tasks, integrity verification tasks, and chain anchoring evidence.

### 6.6.1 Resource Model and Request Model

```typescript
/**
 * Audit record view: an audit log together with its integrity verification result.
 * Audit records use the dual tamper-resistance of "source-side signing + storage-side chained hashing" (see 5.6.2); the integrity field exposes its verification status.
 */
export interface AuditRecordView {
  /** Unique ID of the audit record on the AMP side. */
  auditId: string;
  /** Corresponding source-side log ID. */
  logId: string;
  /** Time at which the event occurred. */
  timestamp: string;
  /** Principal that produced the log. */
  aic: string;
  /** Distributed trace link ID. */
  traceId?: string;
  /** Business correlation ID. */
  correlationId?: string;
  /** ID of the hash chain it belongs to (records in the same chain form a tamper-resistant chain in order). */
  chainId: string;
  /** Sequence number within its chain (auto-incrementing); together with chainId it locates the record. */
  chainSeq: number;
  /** Audit content body (actor/action/target/result); for the structure definition see 5.6 AuditBody. */
  body: AuditBody;
  /** Integrity verification information: the verification status of the signature and the hash chain. */
  integrity: {
    /** Signature algorithm, such as "EdDSA", "ES256". */
    signatureAlg: string;
    /** Key ID of the public key used for signing. */
    signatureKeyId: string;
    /** Whether the source-side signature passed verification. */
    signatureVerified: boolean;
    /** Time of the most recent signature verification. */

      | "signature"
      | "missing_public_key"
      | "hash_chain"
```

### 6.6.4 Query Constraints and Error Codes

- `records/query`, `summary/aggregate` and `export` must carry a `timeRange`.
- `integrity/verify` must provide at least one of `recordIds`, `timeRange` and `filter`; when `filter` is present, `timeRange` must also be present.
- In v1, even when `integrity/verify` finds an integrity failure it returns `200` with a non-empty `failures` ("finding an integrity failure" is a normal verification conclusion and is not mapped to 4xx); `AMP_AUDIT_VERIFICATION_FAILED` (422) is reserved for a future strict mode that "asserts that everything passes".
- v1 online queries do not support deep queries of `body.target.before/after` and `raw_log`.
- `records/query` sorts by `timestamp desc` by default; v1 allows sorting only by `timestamp`, or by `chainSeq` when `chainId` is matched exactly.
- `keyword` matches only high-signal fields such as `logId`, actor, action, target and result errorCode.
- In v1, export is always executed asynchronously; `downloadUrl` must be short-lived and generated on the fly.

| `AMP_AUDIT_KEY_UNAVAILABLE`     | 503  | The signing public key is temporarily unavailable (for example, ATR is unreachable)                                                                                        |

## 6.7 System API Specification

The System API prefix is `{AMP_BASE_URL}/system`, used to query system log events. The `body` of a system log may be extended freely; the protocol constrains only the stable peripheral fields and the restricted keyword search.

### 6.7.1 Resource Model and Request Model

```typescript
/**
 * System event view: a normalized projection of the peripheral fields of a system log.
 * The system log body is freely extensible, and the protocol constrains only these stable peripheral fields; the raw content is placed in rawBody, and no deep structured query is performed.

export interface SystemEventView {
  /** Unique ID of the source-side log. */
  logId: string;
  /** Time at which the event occurred. */
  timestamp: string;
  /** Principal that produced the log. */
  aic: string;
  /** Normalized numeric severity level (for the value convention see 5.1 SeverityNumber). */
  severityNumber: number;
  /** Original text of the severity level, such as "INFO", "ERROR". */
  severityText?: string;
  /** Distributed trace link ID. */
  traceId?: string;
  /** Business correlation ID. */
  correlationId?: string;
  /** Normalized log message body; this is the main target of keyword full-text search. */
  message: string;
  /** Log category. */
  category?: string;
  /** Name of the component that produced the log. */
  component?: string;
  /** Name of the module that produced the log. */
  module?: string;
  /** Normalized tag key-value pairs. */
  tags?: Record<string, string>;

}
```
