AIA: Agent Identity Authentication Process (ACPs-spec-AIA-v02.02)

# 1. Document Definition

This document is the definition of the Agent Identity Authentication (AIA) process in the ACPs agent collaboration protocol suite, version v02.02.

The full title of the document is ACPs-spec-AIA-v02.02.

Document authors: Ke Yu (Beijing University of Posts and Telecommunications), Haozhe Song (Beijing University of Posts and Telecommunications), Yinming Li (Beijing University of Posts and Telecommunications), Jun Liu (Beijing University of Posts and Telecommunications), Ke Li (Beijing University of Posts and Telecommunications), Keliang Chen (Beijing University of Posts and Telecommunications), Xiaofeng Hu (Beijing University of Posts and Telecommunications), Di Ma (Beijing University of Posts and Telecommunications).

# 2. Introduction to the Agent Identity Authentication Process

For agent interconnection to become a secure and reliable agent system, the agents running within it with the ability to execute tasks autonomously should be secure and reliable entities. In the agent trusted registration process standard of the ACPs protocol suite, two necessary conditions are provided for each agent: the Agent Identity Code (AIC) and the Certificate of Agent Identity (CAI). This document defines the detailed process by which agents satisfying these two conditions perform identity authentication.

# 3. Definition of the Agent Identity Authentication Process

Agent identity authentication can use a variety of authentication protocols. mTLS with the TLS 1.3 protocol is recommended. The agent that initiates the request is the mTLS client (Agent1 in the figure), and the agent that accepts the request is the mTLS server (Agent2 in the figure). The agent identity authentication process is mainly divided into three steps: key exchange (Key Exchange), server parameters (Server Parameters), and authentication (Authentication). Apart from the key exchange part, all other steps are carried out in encrypted form.

First is the key exchange, which includes:

(1) The client sends a ClientHello message, containing:
* A random number: used for key derivation.
* A list of supported TLS protocol versions.
* Cipher Suites: a set of symmetric encryption algorithm/HKDF hash algorithm pairs.
* Certificate Authorities: specifies the supported CASPs; the server subsequently needs to return a certificate issued by the corresponding authority.
* signature_algorithms: provides the hash algorithms for certificate signatures that the client can perform, ensuring that the client can verify the certificate, such as ECDSA and RSA-PSS.
* supported_groups: provides the elliptic curves for the ECDHE algorithm that the client supports, such as x25519 and secp256r1.
* key_share: contains the elliptic curve or finite field parameter group used and the ephemeral public key generated by the client.
* psk_key_exchange_modes: used to specify the PSK key exchange modes supported by the client, such as PSK-only or PSK with (EC) DHE.
* pre_shared_key: used to provide support for PSK mode during the TLS handshake.
* Other extension fields may also be included.

(2) The server replies to the client with a ServerHello message, containing:
* A random number: used for key derivation.
* The selected TLS protocol version.
* The selected Cipher Suites.
* key_share: contains the elliptic curve or finite field parameter group used and the ephemeral public key generated by the server.
* pre_shared_key: if the client used pre-shared key (PSK) mode, the server confirms the PSK used here.
* Other extension fields may also be included.

(3) The server and the client use the ephemeral public key in each other's key_share together with their own ephemeral private key to negotiate a shared symmetric key through the ECDHE algorithm, and then use the HKDF algorithm to derive multiple keys for encrypted communication. All messages sent afterwards are encrypted messages. Key exchange is complete;

Then come the server parameters, which include:

(4) The server sends Encrypted Extensions (used to carry responses to those ClientHello extensions that are not used to determine encryption parameters) and CertificateRequest (indicating that the client is required to send a client certificate);

Finally comes authentication, which includes:

(5) The server sends the CAI (server certificate), CertificateVerify (selecting a signature algorithm provided by signature_algorithms in the ClientHello, and then using the private key corresponding to the public key in the server certificate to sign the hash value of all previous handshake messages), and Finished (handshake finished);

(6) After receiving the server's CAI and CertificateVerify, the client first performs identity verification of the server. The verification steps are as follows:
* After receiving the server's CAI, the client verifies the server's CAI through the following steps:

    ①　Separate the plaintext and the signature of the CAI, then map the plaintext using the same hash algorithm as the CASP to obtain the digest Hash1.

    ②　Using the CASP's public key, perform a signature verification operation on Hash1 and the signature in the CAI according to the signature algorithm adopted by the CAI (such as ECDSA or RSA-PSS).

    ③　If the signature verification passes, it indicates that the CAI has not been tampered with and that all plaintext information in it is trustworthy.

    Then verify the plaintext information in the CAI, mainly comparing the peer's AIC with the AIC in the CAI.

* After receiving the server's CertificateVerify, the client uses the signature algorithm specified by signature_algorithms and the public key in the peer's certificate to perform a signature verification operation on the signature in CertificateVerify; the data being verified is the hash value of all handshake messages. If the verification passes, it indicates that the server indeed holds the private key corresponding to the public key in the CAI and that the handshake messages have not been tampered with.

(7) After the client has successfully verified the server, it sends the CAI (client certificate), CertificateVerify, and Finished (handshake finished) to the server;

(8) After receiving the client's CAI and CertificateVerify, the server verifies the client's CAI and CertificateVerify by the same steps; after both sides have each verified that the received Finished content is correct, the mTLS handshake is complete.

(9) After successful verification, encrypted data transmission can begin.

After the mTLS handshake is complete, the communication framework **MUST** pass the peer AIC extracted from the CAI to the upper-layer protocol processing logic as the peer AIC. When upper-layer protocols such as AIP enable identity binding, they MUST use this peer AIC to perform a consistency check against the `senderId` or an equivalent identity field in business messages.

# 4. User Identity Authentication Process

When a user uses an agent (such as a personal assistant), it is recommended to use the OIDC protocol to verify the user's identity. The main process is as follows:

(1) The user requests a service from the personal assistant agent;

(2) The personal assistant agent redirects the user to an authentication server (a third party) to perform the login operation;

(3) The authentication server asks the user for the account and password;

(4) The user provides the account and password to the authentication server;

(5) After successful authentication, the authentication server generates an ID Token, an Access Token, and so on, and returns them to the personal assistant agent;

(6) The personal assistant agent uses the authentication server's public key to decode the received ID Token and verifies the validity of the signature as well as fields such as iss, sub, and aud. Once verification is complete, the user's legitimate identity has been successfully authenticated.

# 5. Supplementary Notes

The agent identity authentication process defined in this document fully takes manageability and compatibility into consideration and is provided free of charge to relevant developers and institutions for reference. We welcome other industry colleagues engaged in agent development and the formulation of agent interconnection protocols to support and adopt this process definition, so as to form an agent identity authentication mechanism that favors interconnection and good compatibility.
